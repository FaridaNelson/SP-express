# Development Log — 2026-08-25

## Production Progress Summary Bug Investigation

### Context

A production user reported that the **Progress Snapshot** was not updating consistently after lesson grades were edited.

Observed production example:

- Lesson History showed the latest lesson at **77%**
- Progress graph showed **77%**
- Readiness donut showed **75%**
- Skill Breakdown still showed older piece readiness values

This investigation traced the problem across the production VM, Express API, MongoDB-derived summaries, and the React teacher dashboard.

## 3. Donut Arithmetic Was Correct

The original user report showed these stale Skill Breakdown values:

```text
Piece A = 72%
Piece B = 80%
Piece C = 59%
Piece D = 90%
```

The donut displayed:

```text
(72 + 80 + 59 + 90) / 4
= 75.25
→ 75%
```

The latest lesson showed:

```text
Piece A = 72%
Piece B = 80%
Piece C = 67%
Piece D = 88%
```

which gives:

```text
(72 + 80 + 67 + 88) / 4
= 76.75
→ 77%
```

Therefore the donut itself was not performing incorrect arithmetic.

**The donut was correctly calculating from stale Skill Breakdown data.**

## 5. Relevant Backend Architecture

`scoreEntry.routes.js` currently exposes individual ScoreEntry creation/upsert through:

```text
POST /api/score-entries/
```

`createScoreEntry()` performs an upsert using `ScoreEntry.findOneAndUpdate(...)`.

Its identity filter includes:

```text
createdByTeacherId
studentId
examPreparationCycleId
lessonId
lessonDate
elementId
archivedAt
```

After every individual ScoreEntry upsert, the controller runs:

```js
await recomputeStudentReadModels(safeStudentId);
```

That function recomputes:

1. `ExamPreparationCycle.progressSummary`
2. `StudentDashboardSummary`

This means the mutation unit is **one score element**, while the derived-state unit is **the whole student/cycle summary**.

---

## 6. Root Cause: Concurrent Summary Recomputations

The frontend sends multiple ScoreEntry requests concurrently.

For a Performance cycle this can look like:

```text
POST Piece A
POST Piece B
POST Piece C
POST Piece D
```

Each request independently does:

```text
upsert one ScoreEntry
        ↓
recompute entire exam-cycle summary
        ↓
save progressSummary
```

Because all requests may execute concurrently, separate recomputations can observe different partial states.

Example:

```text
A recompute sees: A=new, B=old, C=old, D=old
B recompute sees: A=new, B=new, C=old, D=old
C recompute sees: A=new, B=new, C=new, D=old
D recompute sees: A=new, B=new, C=new, D=new
```

Database completion order is not guaranteed to match request-start order.

A stale recomputation can therefore finish last and overwrite a newer/correct summary.

This is an **application-level race condition / stale-write race**.

---

## 7. Why New Lesson Creation Can Appear Correct

The React progress hook performs an optimistic update:

```js
setItems(nextItems);
```

before all score-entry requests finish.

This can make a newly scored lesson look correct immediately even if the persisted derived summary is temporarily or permanently inconsistent.

The create workflow can therefore mask the backend race.

The problem becomes visible later through:

- Edit Grades
- page refresh
- another user/session
- a fresh read of persisted summary state

---

## 8. Secondary Robustness Concern

`recomputeExamCycleSummary()` currently resolves ScoreEntries using:

```js
.sort({ lessonDate: -1, createdAt: -1 })
```

Because existing ScoreEntries are upserted, editing changes `updatedAt` while `createdAt` remains unchanged.

Assuming the model uses Mongoose timestamps, this should be reviewed and tested:

```js
.sort({
  lessonDate: -1,
  updatedAt: -1,
  createdAt: -1,
})
```

This is **not** the primary race-condition fix, but it may improve latest-score resolution when multiple historical entries share a lesson date or duplicates exist.

---

## 9. Architectural Decision

The permanent fix will align the backend mutation boundary with the teacher's actual business action.

### Current architecture

```text
TEACHER ACTION
Save today's progress

        ↓

POST Piece A → recompute whole summary
POST Piece B → recompute whole summary
POST Piece C → recompute whole summary
POST Piece D → recompute whole summary
```

### Target architecture

```text
TEACHER ACTION
Save today's progress

        ↓

API COMMAND
saveLessonProgress()

        ↓

DATABASE
Lesson
ScoreEntries A/B/C/D

        ↓

ALL SCORE WRITES COMPLETE

        ↓

recomputeStudentReadModels() ONCE

        ↓

RESPONSE
authoritative updated progress
```

Recommended route for the permanent solution:

```text
PUT /api/lessons/:lessonId/progress
```

The endpoint should accept all lesson score elements and their metadata as one logical command.

---

## 10. Planned Migration Strategy

To reduce regression risk:

1. Keep the existing `POST /api/score-entries/` endpoint during migration.
2. Extract reusable ScoreEntry validation/upsert logic into a service.
3. Add a lesson-progress endpoint.
4. Upsert all lesson ScoreEntries before recomputing summaries.
5. Prefer `ScoreEntry.bulkWrite()` for the group of element mutations.
6. Call `recomputeStudentReadModels()` exactly once.
7. Return the authoritative `cycleSummary` / `studentSummary`.
8. Migrate the React teacher scoring/edit workflow to the new command.
9. Remove/deprecate the old multi-request path only after production verification.

A MongoDB transaction may be added later as hardening, but it is not required for the first permanent fix.

---

## 11. Temporary Mitigation

If a production hotfix is required before the permanent endpoint is completed, replace concurrent frontend ScoreEntry writes with sequential writes.

Instead of:

```js
await Promise.all(promises);
```

use a sequential loop:

```js
for (const item of itemsToSave) {
  await saveScoreEntry(item);
}
```

This ensures each existing recomputation completes before the next score is written.

This is safer but inefficient because the full summary is still recomputed once per element.

It should be treated as a temporary mitigation only.

## Key Engineering Lesson

> The boundary of a write operation should usually match the boundary of the business operation.

For StudioPulse, the business operation is:

```text
Save today's lesson progress
```

not:

```text
Save Piece A
Save Piece B
Save Piece C
Save Piece D
```

Concurrent I/O is useful, but concurrent operations that read and overwrite the same shared derived state can create timing-dependent correctness bugs.
